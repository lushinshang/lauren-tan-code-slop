章節 1：把 slop 變成黃金（00:00）

00:16 好的，再次自我介紹，我的名字是 poteto。我在 SpaceXSI 負責 Grok Bot。大家可以快速舉個手嗎？你們當中有多少人曾看過別人寫的程式碼，心裡想著「這全都是低品質的雜訊程式碼（slop）」？嗯，我也曾經這樣覺得。但今天我要說服你們，你可以把那些 slop 變成黃金。上個月我做了一件很瘋狂的事，我把 3,000 個 PR 發布到了正式環境。

00:48 在有 agent 之前，除了一些極端案例之外，我們其實從來不在乎數量。而在我前一家公司，我們稱這些人為寫程式機器。像 Bret Taylor 這樣的人，他最著名的就是在一個週末內重寫了整個 Google Maps。完全是個生產力高到不可思議的工程師。而現在有了 agent，任何人都可以成為寫程式機器。我的論點是，軟體工程師的工作，身為軟體工程師的核心本質，就是在大幅提升生產力的同時，找出如何維持甚至改善程式碼品質的方法。

01:23 為了達到這個境界，有些人喜歡稱之為軟體工廠（software factory）。但我喜歡保持簡單，我認為這一切都關乎信任。不是盲目的信任，而是投資在你的 agent 環境上，讓你能夠信任你的 agents 會做正確的事。要達到這個境界需要付出相當多的心力，我花了 6 個月才達到可以交付數千個 PR 的狀態，其中很多甚至是在我睡覺時完成的。但這絕對是可能的，而且你們花的時間會比我少得多。

01:56 所以我們先來談談如何從低信任度轉變為高信任度的環境。

章節 2：信任金字塔與程式碼庫品質（02:03）

02:05 這座倒金字塔就是我對於該把時間花在 agent 環境哪裡的思考方式。前兩層是確定性的，也就是運用你的程式碼本身。像是良好的 API 設計、架構、重構，或是使用 lint 規則、型別系統、編譯器，或是各種類型的測試。你可以結合這兩層來約束 agents 能做的事情，並迫使它們預設就做正確的事。驗證（包含執行期驗證與形式驗證）是很棒的工具，可以疊加進來找出 bug 並檢查屬性

02:39 以及你希望在系統中始終維持的不變量，同時也能幫你檢查 agent 是否理解了你的目標與意圖。最後，你會想疊加一點自然語言的描述。像是 rules、skills、AGENTS.md，這些需要判斷力的事情。但我們先從你的程式碼庫（codebase）開始。Agents 是根據輸入來產生輸出的。所以輸入的品質非常重要，而剛好你的程式碼庫就是最大的輸入來源之一。

03:12 因此，每當你在糾正 agent 時，請思考如何將它變成確定性檢查，而不是在 rules 或你的 AGENTS.md 裡多加一行，因為寫進程式碼裡的可重現性高得多，也能讓你更加信任它。我喜歡用的比喻是，你的程式碼庫有點像一座花園。過去程式碼一次只會有幾個 PR 送進來。我記得 2024 年去上班時，審查了我同事寫的那 3 個 PR。

03:44 而今天，那個數字更像是 300 個。所以現在每位工程師都是由數百甚至數千個 agent 組成的團隊，程式碼湧入得如此迅速，幾乎就像是一條持續不斷的水流，甚至感覺很像有機的生命體。在這個比喻中，你的程式碼庫、你施加的約束條件、你設立的護欄，就是水泥地基，讓你的 agents 所寫的新程式碼圍繞著它生長，就像這張圖片中的建築物一樣。

04:18 所以在許多方面，身為軟體工程師的工作有點變得像是在園藝。因為程式碼是 agent 最大的輸入，這意味著任何權宜之計（workaround）、反模式、棄用程式碼、技術債，現在都很可能會直接被下一個 agent 複製，因為它看起來就像是你程式碼庫中既有的模式。這就像你的花園裡長了一些雜草或害蟲，不知不覺中它們就蔓延得到處都是。

04:53 所以你要盡可能讓你的程式碼庫保持純淨無暇，這樣 agents 才會總是複製好的東西。好，我們來看一些真實的範例。

章節 3：Dune 與可強制執行的架構（05:00）

05:00 Dune 是我們為 Grok Bot 建立的客戶端框架，用來實踐這種有機架構的想法。技術上來說它其實沒有那麼有趣。你大概可以把 Dune 想成有點像 Electron 應用程式的 Next.js。但 Dune 有趣的地方在於它有許多約束和 lint 規則，我們將打造桌面應用程式學到的許多經驗教訓都編寫進去了。其中一個經驗教訓是：任何需要細微拿捏才能用好的東西，往往都會導致 slop。

05:33 最經典的例子就是 React 裡的 useEffect，對吧？它有適用的使用情境，但經常被誤用。有些人開玩笑說你需要博士學位才能用好 useEffect。換句話說，它真的需要非常細微的拿捏才能用好。而 agents 並不擅長使用它。所以我們的解決方案就是直接在產品程式碼中禁用它，只允許在 Dune API 內部的少數地方使用。實際上，這個問題現在已經被徹底根除了，我們再也不需要在程式碼審查時去抓這個問題。

06:10 我們使用的另一個有趣模式是透過目錄結構來提供脈絡。我們在 Cursor（這也是個 Electron 應用程式）上看到的一個反模式是，agents 常常會把主執行緒的程式碼匯入到渲染執行緒中，從而導致長任務與畫面卡頓。所以在 Grok Bot 和 Dune apps 中，我們把它做得非常依循慣例。我們有這兩個頂層目錄，名稱就叫做 electron-renderer 和 electron-main，它們之間的互相匯入會被我們的相依圖分析器與一些 lint 規則禁止。

06:46 再說一次，這些都是很容易設定的簡單 lint 規則，但這意味著在程式碼審查時，我們又少了一件需要審查和思考的事情。

章節 4：用 lint 規則取代註解（06:56）

06:57 然後我看到的另一件更令人驚訝的事，是 agents 使用 Markdown 的方式。像是文件、程式碼註解、rules 或 skills，它們把這些地方當成寫下「自己為何不做正確事情」的藉口之處。或者不知道你們有沒有遇過，它們會對你做出的微小修正矯枉過正，把它當成永遠不可打破的硬性規則。這是 Cursor 的另一個例子。agents 非常喜歡使用命令式的計時器，像是 setTimeout、requestAnimationFrame、requestIdleCallback。

07:32 它們把這些當成權宜之計，因為它們實際上是在掩蓋 VS Code 的命令式風格與 React 的宣告式風格之間的架構衝突。所以我們的架構選擇實際上讓客戶端和 agent 的效能都變差了許多。如果你曾經做過任何 JavaScript 的效能調校，你就會知道當有大量的計時器被快速建立又銷毀時，會引發大量的重大垃圾回收，進而造成嚴重的延遲與畫面卡頓。

08:03 但最糟糕的部分是，agents 寫了大量的程式碼註解（就像你在這裡紅色標示處看到的），解釋為什麼這個權宜之計是合理的。不知不覺中，計時器蔓延得到處都是，應用程式的效能也受到了實質的損害。

08:22 現在在 Grok Bot 中，我們學到了教訓，決定直接禁用 99% 的註解，因為它們很容易過期失準。反正人類本來就懶得去讀那些註解 slop。而且這再次給了 agent 一個後門藉口，以「因為很難」為由來合理化不做正確事情的行為。不過註解最糟糕的一點，是它們無法強制執行。所以看似出於好意（像是「我要告訴下一個 agent 不要這樣做」），最終卻從來不是真正能讓你信任的東西。

08:54 所以在 Grok Bot 和 Dune 中，我們現在有 lint 規則可以提供良好 且非常有幫助的錯誤訊息，告訴 agent 要去修復根本原因、真正的問題，而不是只在周圍打補丁。因此我們的一般原則是，每次我們糾正 agents 時，都會轉化為這些確定性檢查之一，或者我們會思考如何透過更好的 API 設計、更好的架構，在程式碼中徹底根除該問題。如果你重複這樣做夠多次，你會發現程式碼審查時需要留意的東西就變少了。

09:30 到了某個時間點，你會意識到已經沒有什麼需要審查的了。你就可以直接讓 agents 自行合併它們大部分的 PR。

章節 5：執行期驗證與功能地圖（09:40）

09:43 好的。接下來，驗證也是我們讓 agent 更加自主、同時提升我們對它們工作的信心與信任非常關鍵的一部分。我們的程式碼審查流程現在實際上已經縮減為改看驗證產物（verification artifacts）。像是影片、螢幕截圖、圖表、形式驗證。最基本的例子就是執行期驗證（runtime verification），這只是一種花俏的說法，意思是讓你的 agent 能夠親自執行程式碼，並使用除錯工具，就像人類開發者也會使用的工具一樣，例如 Chrome DevTools protocol。

10:16 在我們的執行期驗證 skills 中，我們有一個叫做功能地圖（feature map）的東西。那基本上有點像是從使用者角度出發，列出應用程式中所有可用功能的網站地圖。有了這個，當你說「左側邊欄的那個小東西」時，agents 就不需要瞎猜，它為你們提供了一套共通詞彙。我們在這些 skills 內部也使用了客製化 CLI，讓 agents 每次都能重複使用該 CLI 和 driver，這減少了 token 消耗，同時也是可測試的。

章節 6：形式驗證與 UI 測試（10:50）

10:52 最近我們也開始著眼於形式驗證（formal verification）。我們現在使用 TLA+ 來對主要使用者流程進行模型檢驗，例如跨多裝置與多平台的通知流程。我們也使用 Lean 來證明特定演算法。例如，我們自己寫了一套客製化的虛擬化函式庫，我們在那裡使用 Lean 來檢查不會出現畫面閃爍或抖動的問題。整體而言，我們仍在對這種方法進行實驗。它看起來非常具有前景。透過形式驗證，我們已經找出了相當多的 bug。

11:25 但這當然不是萬靈丹，我們把它當作 agent 環境中的另一個工具、另一個層次。雖然這段影片放得很快，但我們剛開始探索的另一件事，是針對 UI 進行屬性測試（property-based testing）。我們使用了一個叫做 Bombadil 的函式庫。這也已經幫我們抓到了幾個 UI bug。

章節 7：把 token 花在驗證上（11:51）

11:53 好，放大視野來看，我看到了 Cindy Sridharan 的這則推文，6 個月前她說—— 她當時提到因為合併進來的細微 bug，導致她無法信任自己的 agents。而對她來說，能夠信任 agents 所真正欠缺的，就是驗證流程。現在 6 個月過去了，她說她每天 70% 的 token 都花在驗證上。而我認為這也符合我的觀察，我大部分的 token 用量也都花在驗證上。如果你仔細審視她的流程，這裡的每一項技術都不是我們以前從未見過的新奇手法。

12:30 這些都只是良好的軟體工程工具，只是過去因為難以理解、撰寫或維護，使用成本可能高得令人卻步。但 agents 大幅降低了這項成本。說真的，我們正在進入軟體測試與驗證的黃金時代，因為 agents 讓我們能夠對所有事物進行測試，其深入程度遠超越以往具備經濟效益的範疇。形式驗證也能幫助你更好地推導你的產品應該如何運作，以及你的 agents 是否真正理解你的意圖與目標。

13:02 我在我的外掛 pstack 中製作了這個名為 statechart 的新 skill，它可以幫助你從使用者的角度將狀態機視覺化。我發現將這個搭配我們提供的影片和螢幕截圖一起審查，變得容易許多。所以效果很好。抱歉，白底投影片閃到大家了。好，現在我們來看看所謂的應許之地是什麼模樣。這一切的投資能為你換來什麼回報？

章節 8：11,000 個 PR 與約 0.5% 的還原率（13:32）

13:32 在 Grok Bot 團隊中，我們的開發速度正在起飛並迅速提升。上個月，我們團隊向正式環境交付了誇張的 11,000 個 PR，這是一個極其瘋狂的數字。我們發布客戶端的步調也加快了。我們大約每天都會發布一個新的穩定版。核心團隊交付的成果也多出許多。我們也有更多臨時或順手貢獻的外部人員（drive-by contributors），他們不一定掌握很多背景脈絡，但他們也都在進行貢獻。

14:06 在 10 月，我們大約有 227 個人貢獻了至少一個 PR。隨著速度加快，你可能會心想：這難道不會變成一團混亂嗎？這難道不會變成一堆 slop 嗎？但事實上，被還原（revert）的 PR 數量在相對比例上反而變低了，穩定維持在約 0.5% 左右。但我認為關於這種交付速度和 PR 數量，真正有趣的是 Grok Bot 的效能不僅保持穩定，

14:40 而且相較於剛推出時，在多個維度上都有所提升。啟動、打字輸入、開啟新對話、切換對話，這一切都變快了。請記住，Grok Bot 目前仍然是一個 Electron 應用程式。所以它是有極限天花板的，對吧？但它已經比市面上許多其他的 agent UI 快上許多。對於一個擁有如此高速度且有這麼多人共同貢獻的 Electron 應用程式來說，我認為表現相當不錯。

章節 9：先打好基礎，再蓋軟體工廠（15:11）

15:11 因此，在你一頭栽進去打造軟體工廠（software factory）並盡可能把所有事情自動化之前，每當你糾正 agent 時，請嘗試先從改善你的程式碼庫（codebase）著手。先從建立一條 lint 規則來防止反模式再次發生開始，接著也清理掉那些舊模式。然後確保你的驗證機制非常健全。無論如何，這些工作大多都是走向自動化的先決條件。如果你的內圈寫程式迴圈（inner coding loop）產出的是 slop，那麼將該迴圈自動化只會產出更多的 slop，

15:42 而你將不得不向這個問題砸入越來越多的 token，而大家都知道那非常昂貴。而一旦你對你的程式碼庫（codebase）、靜態分析、執行期與形式驗證做出這些投入，你就會開始發現有了這些基礎後，很多事情都變得可能，而且你真的能在這些基礎之上輕鬆打造自己的工廠。而當你準備好時，Grok Bot 是打造那個外圈迴圈的絕佳方式。我們有大量的連接器和routines可以啟動 Cursor、雲端 agents 和專案，讓你能夠編排數百甚至數千個 agents。

16:21 舉個簡單的例子，現在每當我們發布新版本時，Grok Bot 都會自動為我們啟動一個新的 Cursor 專案，對整個應用程式進行模糊測試（fuzz），測試整個建置（build），而且它會透過執行應用程式並像真實使用者一樣使用它來找出 bug。接著它會為找到的每個 bug 開立修復 PR，並且會自動合併，聽起來雖然很瘋狂但確實如此。這是因為我們的程式碼庫（codebase）夠優秀，PR 往往預設就品質良好，而且我們合進去的大多數產品程式碼，真的不再需要深入的人工審查。

16:57 所以當你擁有扎實的基礎和良好的有機架構時，你就能把 slop 點石成金，並且能夠高速交付，同時完全不對品質妥協。我是 poteto，大家也叫我 Lauren。再次感謝大家來聽我的演講。〔掌聲〕
